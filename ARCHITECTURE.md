# Архитектура и спецификация asyncTelegramAPI

## 1. Введение и назначение проекта

**asyncTelegramAPI** — полностью асинхронная (event-driven) библиотека Telegram Bot API для микроконтроллеров **ESP8266** и **ESP32**, работающих через **WiFi**.

В отличие от классических библиотек, использующих синхронные блокирующие сокеты (`WiFiClientSecure`) и требующих либо задержек в `loop()`, либо выделения отдельной задачи FreeRTOS на ESP32, данная библиотека построена на базе событийной модели **lwIP** (`AsyncTCP` для ESP32 и `ESPAsyncTCP` для ESP8266).

### Ключевые преимущества:
- **Zero-blocking:** Основной цикл `loop()` свободен на 100% на обеих платформах (ESP8266 и ESP32).
- **Нативный Long Polling:** Соединение пассивно слушает сокет в стеке lwIP без нагрузки на CPU и без блокировки выполнения другого кода.
- **HTTP Keep-Alive:** Постоянное защищённое соединение устраняет накладные расходы на повторные TLS-рукопожатия.
- **Единый знакомый API:** Сохранение сигнатур `TResult`, `callback`, разметки меню `[MENU]`, команд `is_command()` и методов отправки из `microTelegramAPI`.

## 2. Контекст перехода и зафиксированные грабли (Lessons Learned)

При разработке синхронной библиотеки и экспериментах с FreeRTOS был выявлен ряд критических аппаратных и сетевых ограничений, которые заложены в основу архитектуры нового проекта:

### 2.1. Исчерпание сокетов LwIP (Socket Exhaustion)
* **Проблема:** В ESP-IDF по умолчанию доступно всего 4–5 дескрипторов сокетов. При частом закрытии сокета (`client.stop()`) и повторном открытии сокеты зависают в состоянии `TIME_WAIT` (до 30–60 секунд). Серия быстрых запросов приводила к ошибке `No connection to Telegram server`.
* **Решение в asyncTelegramAPI:** Использование постоянного соединения **HTTP Keep-Alive**. Один TLS-сеанс удерживается открытым и используется как для удержания Long Polling, так и для отправки исходящих сообщений. Переподключение выполняется только при таймауте сервера или ошибке сети.

### 2.2. Пакетная обработка входящих сообщений (Burst Updates)
* **Проблема:** Если пришло сразу несколько сообщений (пачка 5 сообщений), отправка ответов подряд без пауз перегружала сокеты и вызывала сбои.
* **Решение в asyncTelegramAPI:** Все исходящие действия помещаются в очередь запросов (Tx FIFO Queue). Отправка следующего запроса инициируется только после подтверждения доставки или завершения предыдущего (`onReadyToSend` / `onDataReceived`), с обязательным защитным квантом времени (10–20 мс).

### 2.3. Ограничения памяти на ESP8266
* **Проблема:** Сессия TLS по умолчанию может требовать до 35–45 КБ RAM (буферы по 16 КБ на вход и выход). На ESP8266 это вызывает моментальное исчерпание кучи (OOM).
* **Решение в asyncTelegramAPI:** Для BearSSL на ESP8266 настраиваются компактные буферы (`setBufferSizes(512, 512)` или динамический буфер `BR_OPT_TOLERANT_MAX_IN_BUFSIZE`).

### 2.4. Безопасные рамки Long Polling и Backoff
* **Правило:** Таймаут Long Polling настраивается в пределах **10..50 секунд** (рекомендуемое значение: 20 секунд).
* **Backoff при сбое:** При обрыве соединения или HTTP-ошибке (например, 429 Too Many Requests) переподключение происходит с паузой **3–5 секунд**, чтобы избежать зацикливания.

```
+-------------------------------------------------------------+
|                        User Sketch                          |
|         setup(), loop() [полностью свободен], callback()    |
+-------------------------------------------------------------+
                              |
+-------------------------------------------------------------+
|                      AsyncTelegramAPI                       |
|   - begin() / setLongPoll() / setInterval()                 |
|   - sendMessage(), deleteMessage(), sendMessageToAll()      |
|   - Tx Queue (Очередь исходящих запросов)                   |
|   - Управление смещением lastUpdateId                       |
+-------------------------------------------------------------+
                              |
+-------------------------------------------------------------+
|                        TelegramCore                         |
|   - TResult структура                                       |
|   - Формирование JSON для getUpdates, sendMessage...        |
|   - Парсинг ответов Telegram (ArduinoJson 7)                |
|   - Парсер меню [MENU], whitelist, is_command               |
+-------------------------------------------------------------+
                              |
+-------------------------------------------------------------+
|                      AsyncHTTPClient                        |
|   - Разбор HTTP-заголовков (Status, Content-Length, Chunked)|
|   - Конечный автомат HTTP (FSM): IDLE, CONNECT, REQ, RESP   |
|   - Удержание HTTP Keep-Alive                               |
+-------------------------------------------------------------+
                              |
+-------------------------------------------------------------+
|                 Транспортный уровень lwIP                   |
|       ESP32: AsyncTCP      |     ESP8266: ESPAsyncTCP       |
|                 (TLS 1.2 / BearSSL / mbedTLS)               |
+-------------------------------------------------------------+
```

## 4. Состояния конечного автомата (FSM)

Асинхронный клиент управляется событиями сокета:

```
                  +--------------+
                  |     IDLE     |<--------------------+
                  +--------------+                     |
                         | (begin / опрос / отправка)  |
                         v                             |
                  +--------------+                     |
                  |  CONNECTING  |                     |
                  +--------------+                     |
                         | onConnect                   |
                         v                             |
        +--------->+--------------+                    |
        |          | SEND_REQUEST |                    |
        |          +--------------+                    |
        |                 | onRequestSent              |
        |                 v                            |
        |          +--------------+                    |
        |          | WAITING_DATA |                    |
        |          +--------------+                    |
        |                 | onData                     |
        |                 v                            |
        |          +--------------+                    |
        |          | PARSING_RESP |                    |
        |          +--------------+                    |
        |                 |                            |
(Keep-Alive: след. запрос)| (Ответ разобран: вызов cb) |
        +-----------------+----------------------------+
```

1. **IDLE:** Нет активных операций.
2. **CONNECTING:** Установка асинхронного TCP + TLS рукопожатия.
3. **SEND_REQUEST:** Передача HTTP-заголовков и тела (JSON) через `client->write()`.
4. **WAITING_DATA:** Пассивное ожидание. При Long Polling клиент может находиться здесь до 20–50 секунд без расхода тактов CPU.
5. **PARSING_RESP:** Потоковый разбор поступивших байт:
   - Проверка HTTP-кода (`200 OK`).
   - Поиск границы заголовков `

` и `Content-Length`.
   - Десериализация тела JSON и передача результата в обработчик `callback`.
   - Если в очереди Tx есть накопившиеся сообщения — переход к `SEND_REQUEST` по открытому сокету.
   - Если сообщений нет — запуск следующего цикла `getUpdates`.

## 5. Целевой пользовательский интерфейс (API)

Пример использования библиотеки в скетче:

```cpp
#include <Arduino.h>
#include <AsyncTelegramAPI.h>

AsyncTelegramAPI bot;

String callback(TResult &msg) {
    if (msg.text == "ping") return "pong";
    if (msg.text == "menu") return "Menu[MENU]btn1	btn2
btn3";
    return "Echo: " + msg.text;
}

void setup() {
    Serial.begin(115200);
    WiFi.begin("SSID", "PASSWORD");
    while (WiFi.status() != WL_CONNECTED) delay(500);

    bot.setBotToken("BOT_TOKEN");
    bot.setChatID(123456789);
    bot.attachCallback(callback);

    // Включаем Long Polling на 20 секунд (рекомендуется)
    bot.setLongPoll(20);

    // Запуск асинхронного движка
    bot.begin();

    bot.sendMessage("Бот запущен асинхронно!");
}

void loop() {
    // В loop() НЕ НУЖНО вызывать checkMessage()!
    // Все сетевые события обрабатываются асинхронно через lwIP.
    // loop() свободен на 100%.

    static uint32_t last = 0;
    if (millis() - last > 60000) {
        last = millis();
        bot.sendMessage("Минутный отчет");
    }
}
```
